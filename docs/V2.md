# SMP v2 — Unit & Department Ownership, Cost Tracking and Smart Features

v1 tracked every subscription and approved requests one by one. v2 makes **units and departments the owners of subscriptions**:

- Every subscription belongs to a **unit** (BMD, AES, …) and optionally to **one department** inside it.
- One unit — and one department — can own **many** subscriptions.
- An employee can only request a seat on a subscription that **their unit owns as a shared (unit-wide) subscription** or that **their own department owns**.
- Cost and card payments are tracked and reported **per unit and per department**, against each one's monthly budget.

---

## 1. Data model changes

```
units                 departments                    employees
─────                 ───────────                    ─────────
id                    id                             ...
code  (BMD, AES)      unit_id ───────► units.id      unit_id ───────► units.id
name                  name                           department_id ─► departments.id
head_employee_id      code                           team (free text, unchanged)
monthly_budget_bdt    head_employee_id
active                monthly_budget_bdt
                      cost_center
                      active
                      UNIQUE(unit_id, name)

subscriptions (changed)                 card_charges (changed)
───────────────────────                 ──────────────────────
owner_scope  'unit' | 'department'      unit_id        (snapshot of owner at charge time)
unit_id ──────► units.id   (required)   department_id  (snapshot; null for unit-shared)
department_id ► departments.id          anomaly        (true if amount is unusual)
   (required when owner_scope =         anomaly_note
    'department', must belong to unit)
```

- `employees.unit` / `employees.department` text columns become foreign keys to the new tables.
- `subscriptions.unit` / `subscriptions.department` text columns become `unit_id` / `department_id` + `owner_scope`.
- Charges copy the owner **at the moment they are recorded**, so moving a subscription to another department later never rewrites past payments.

## 2. Access rule — who can request what

| Subscription owner | Who can request a seat |
| --- | --- |
| Unit-wide (`owner_scope = unit`, e.g. *AES – Claude Team*) | Every active employee of that unit |
| Department (`owner_scope = department`, e.g. *AES / IT – GitHub Copilot*) | Only employees of that department |
| Another unit or department | Nobody — the request is refused |

- The request form only lists **`GET /api/my/available-subscriptions`**: subscriptions the employee is allowed to use, with free seats and monthly cost per seat.
- `POST /api/requests` (type `new`, `renewal`, `upgrade`, `cancel`) **must** reference one of those subscriptions; anything else returns `403`.
- A tool the unit/department does **not** have yet is requested as a **proposal** (type `proposal`), which only a **department head, unit head or reporting manager** can raise. Approval follows the same manager → DMD Sir path; once approved, DMD Sir or a delegate adds the subscription to the register owned by that department and links it (`POST /api/requests/{id}/fulfil`). After that, employees request seats normally.

## 3. How department and unit cost is calculated

Two views, same as v1:

| View | Meaning |
| --- | --- |
| **Accrued** (default) | Each subscription's cost spread evenly over the days it is active (monthly charge ÷ days in month, yearly charge ÷ days in year) |
| **Paid** | Actual card charges on their charge date, using the owner snapshot stored on each charge |

**Accrued cost per department** has three parts:

1. **Direct** — 100% of every subscription the department owns.
2. **Allocated share of unit-wide subscriptions** — each day, a unit-wide subscription's daily cost is split equally across the seats bought, and each held seat's share goes to its holder's department.
3. The share of **empty seats** on a unit-wide subscription goes to the unit's **Shared pool** line (visible waste — a reason to cut seats).

So: **unit total = Σ department totals + shared pool**, and every taka is counted exactly once.

Example (one month, AES unit):

| Subscription | Owner | Monthly cost | Seats held by | Goes to |
| --- | --- | --- | --- | --- |
| Claude Team, 3 seats | AES (unit-wide) | ৳ 33,075 | 2 × IT, 1 × Finance | IT ৳ 22,050 · Finance ৳ 11,025 |
| GitHub Copilot | AES / IT | ৳ 1,225 | IT | IT ৳ 1,225 (direct) |
| ChatGPT Team, 2 seats | AES (unit-wide) | ৳ 7,350 | 1 × Finance, 1 empty | Finance ৳ 3,675 · Shared pool ৳ 3,675 |

→ IT ৳ 23,275 · Finance ৳ 14,700 · Shared pool ৳ 3,675 · **AES total ৳ 41,650**.

**Budgets** — each unit and department has `monthly_budget_bdt`. The API returns month-to-date spend, projected month-end spend (MTD ÷ days elapsed × days in month), % used, and a status: `ok` (< 80%), `warning` (80–100%), `over` (> 100%). Crossing 80% and 100% notifies DMD Sir, delegates and the unit/department head.

## 4. How to fetch the data (API)

All endpoints need `Authorization: Bearer <token>`. DMD Sir and delegates see everything; a **unit head** sees their unit; a **department head** sees their department; managers keep the v1 team view.

### Unit totals

```http
GET /api/costs/units?from=2026-10-01&to=2026-10-31&view=accrued
```

```json
{
  "from": "2026-10-01", "to": "2026-10-31", "view": "accrued",
  "rows": [
    {"unit_id": 2, "code": "AES", "name": "AES", "amount_bdt": "41650.00", "amount_usd": "341.39",
     "paid_bdt": "40100.00", "subscriptions": 3, "seats_used": 5, "seats_total": 6,
     "budget_bdt": "50000.00", "projected_month_bdt": "41650.00", "budget_used_pct": 83.3, "budget_status": "warning"}
  ],
  "total_bdt": "41650.00"
}
```

### One department in detail

```http
GET /api/costs/departments/5?from=2026-10-01&to=2026-10-31
```

Returns the department's totals plus `subscriptions` (owned + unit-wide ones its people use, with each one's share), `employees` (cost per person) and `trend` (last 12 months).

    print(u["code"], u["amount_bdt"], u["budget_status"])

| POST | `/api/requests` | everyone | `subscription_id` now required, except `type: "proposal"` |
| POST | `/api/requests/{id}/fulfil` | admin | Link an approved proposal to its new subscription |

| GET | `/api/costs/units` | admin, unit heads | Unit totals, seats, budget |
| GET | `/api/costs/units/{id}/departments` | admin, unit heads (dept heads: own row) | Direct / allocated / pool |
| GET | `/api/costs/departments/{id}` | admin, unit head, that department's head | Subscriptions, people, 12-month trend |
| GET | `/api/costs/trend?group=unit|department` | admin, heads | Chart series |
| GET | `/api/costs/payments?group=unit|department` | admin, heads | Card payments by owner |
| GET | `/api/costs/budgets` | admin, heads | This month vs budget |

## 5. Smart features in v2

| Feature | What it does | Endpoint |
| --- | --- | --- |
| **Budget guard & forecast** | Per unit/department budget, projected month-end, status, alerts at 80% / 100% | `/costs/units`, `/costs/budgets` |
| **Savings finder** | Flags (a) empty seats on paid subscriptions, (b) 3+ individual seats of the same tool in one unit that a team plan would cover, (c) seats unused (no receipt confirmed) after 30 days | `GET /api/insights/savings` |
| **Charge anomaly detection** | A recorded charge more than 15% above the expected cost (cost per cycle × FX) is flagged and DMD Sir is notified | automatic on `POST /charges`; `GET /charges?anomaly=true` |
| **Proposals for new tools** | Heads/managers propose a new tool for their department with a business case; approved proposals become department-owned subscriptions | `type: "proposal"` + `/requests/{id}/fulfil` |
| **Owner-safe payment history** | Charges keep the unit/department that owned the subscription at payment time | automatic |

## 7. Migration from v1

1. Create units (`BMD`, `AES`) and departments (from the distinct department names already on employees).
2. Link each employee to their unit and department.
3. Set `owner_scope`, `unit_id`, `department_id` on each subscription (import file has `unit_code`, `department`, `owner_scope` columns).
4. Back-fill `unit_id` / `department_id` on old charges from their subscription.

There are no Alembic migrations yet, so for a fresh install just run `python -m scripts.init_db` (or generate the initial migration) and `python -m scripts.seed`.
